`cpp_unused = auto|required|off`가 C/C++ scope를 선택한다. `off`는 C++ path를 discovery에서만
식별하고 candidate bytes를 읽거나 source intake에 넣지 않으며, standalone의 compilation
context/tool probe도 요청하지 않는다. C++ scope만 명시적으로 건너뛰고 Python 분석은 유지한다.
canonical compilation database가 덮는 모든 owned 및 configured external production translation
unit을 configuration별로 sanitized direct compiler replay하고, warning suppression을
제거·완화한 뒤 `-Wunused-function`과 discarded assembly(`-S`, no link)를 사용한다. 허용되는
실행 파일은 capability-approved
GCC/Clang driver와 approved alias뿐이다. 관측된 family가 GCC이고 version 9 이상이면 structured
JSON diagnostics를, older GCC와 approved Clang-family driver/alias는 bounded parseable text를 사용한다. 같은
executable에서 관측된 Clang family는 `g++` alias spelling보다 우선하고, ici가 controlled
`-fdiagnostics-show-option`을 강제한다. 한 source의 알려진 모든 configuration에서
같은 위치의 compiler warning이 확인될 때만 `Compiler:-Wunused-function` exact finding을 만들며,
clean source도 위치 있는 PASS target으로 남긴다. `ToolEvidence`에는 실행별 tool argv/version과
process 상태를, `cpp_unused_details`에는 finding별 normalized `diagnostic_message`를 분리해
보존한다.

compiler family는 bounded version banner에서 식별하므로 neutral executable이나 `g++` 이름의
Clang alias를 filename/numeric version만으로 GCC로 오인하지 않는다. option separator 뒤에는
canonical source operand 하나만 허용하고 extra operand, second separator, operand 위치의 `-w`는
`extra-compiler-operand`로 실행 전에 거부한다. GCC standard-library include projection cache는
approved compiler identity와 replacement-sensitive working-directory identity(device/inode/mode/
mtime/ctime)를 함께 key로 사용한다. cwd는 lookup 전, cache hit 반환 전, include probe 후에
재검증하며 replacement 또는 metadata change는 cache miss 또는
`gcc-include-probe-cwd-changed` fail-closed가 된다.

이 slice의 주장은 선택된 source-owned 또는 configured external TU 안의 compiler-diagnosed
unused-function 정의에만 한정된다. canonical compilation context/database digest, production TU
coverage가 필요하고,
context의 `unity_build=true`는 source ownership을 증명할 수 없으므로 거부한다. 각 unit의
working-directory identity와 source snapshot을 replay 전·후에 확인하고, unit configuration
digest는 directory/argv/output에서 다시 계산해 canonical identity와 대조한다. selected unit의
language는 정확히 `c` 또는 `c++`여야 하며, 비어 있거나 Objective-C 계열인 unit은 compiler를
실행하기 전에 거부한다. header/non-TU
diagnostic 중에서도 exact `-Wunused-function` warning이 선택된 TU 밖을 가리키는 경우만
`cpp_unused_non_tu_diagnostics_excluded`에 세며, 그 밖의 diagnostic은 세지 않는다. matching
`-Wunused-function` warning에 source location이 없거나 위치를 판별할 수 없으면 excluded count로
세지 않고 fail-closed한다. accepted source position은 compiler가 보고한 logical path가 selected
TU와 정확히 같고 line/column 범위가 immutable source snapshot 안에 있을 때만 보존한다. 범위를
벗어난 `#line` 또는 macro remapping은 fail-closed하며 physical macro-definition origin은
재구성하지 않는다. external-linkage symbol, template, inline/COMDAT,
whole-program/linker reachability, dynamic lookup, plugin, Qt meta-object reachability는 판정하지
않는다. 공통 bounded intake/replay 한도(8,192 candidate path, 2,048 owned files/TU, 파일당
8 MiB·aggregate 64 MiB, output 1,000,000자, TU당 120초·전체 600초)도 적용한다.

context/database/ingestion/replay/process/parser/output/location/duplicate/configuration-disagreement,
source snapshot·compiler·working-directory identity 변경, timeout·truncation·budget 초과는
partial finding 없이 fail-closed한다. C++ probe는 atomic하며 replay/process/parser 오류에는
fail-fast로 이미 모은 C++ observation/finding을 폐기하고 이후 compiler unit을 실행하지 않는다.
최종 merge에서 발견된 configuration disagreement도 모든 C++ finding을 폐기한다. 이미 성공적으로
완료·기록된 compiler observation의 source에는 exact PASS/WARN 대신 위치가 있는 `C++UnusedFunctionsInvalidated` `SKIP` target을
남겨 폐기 범위를 추적한다. hybrid에서
이미 완료한 Python finding은 유지하며, Python은 `ESTIMATED`/`python-ast-heuristic`, native C++
finding은 `EXACT`와 compiler/tool-rule attribution(`tool_name`, `tool_rule_id = "-Wunused-function"`)을 유지한다. 두 scope가 모두 완료된
경우 aggregate는 보수적으로 `ESTIMATED`이고, C++ 실패 시 aggregate status/evidence는 그
실패를 반영한다. unavailable context/tool은 exact PASS로 승격하지 않는다. C++-only project의
`auto`는 `required = false`인 `SKIP`/`NOT_RUN`으로 남아 suite에 optional `WARN`을 기여하고,
`required`는 `ERROR`/`NOT_RUN`, `off`는 명시적 `SKIP`이다. context가 존재한 뒤 드러난 invalid
context/coverage/configuration/replay/parser/identity 오류는 `auto`와 `required` 모두
`ERROR`/`NOT_RUN`으로 닫는다. standalone `ici dead`는
`DeadCodeEngine`의 context 요구를 통해 `prepare_analysis_context`로 같은

preflight 이후 database가 바뀌면 다음 preflight가 새 digest와 새 immutable context를 만든다.

CTest JUnit `<skipped>`와 `status="notrun"`/skip/skipped/disabled/blacklisted, stdout의

렌더링한다.

QtTest parser는 `-xunitxml`의 각 `<testcase>` 상태를 해석한다. qmake adapter에서는
`make check` transcript가 테스트 바이너리 하나를 권위 있는 scope로 세고, QtTest XML은
그 바이너리의 failure detail을 보강하는 데만 사용한다. 따라서 QtTest와 자체 `main()`이
섞인 qmake 프로젝트에서 모든 function-level skip을 개별 scope로 집계한다고 주장하지 않는다.

sanitizer는 build 성공을 test 실행 증거로 간주하지 않는다. required 정책은 모든 case가
미실행이거나 실행된 case와 미실행 case가 섞인 경우 모두 `ERROR`/`NOT_RUN`으로 올리며,
실행된 실제 failure target은 `FAIL`로 보존한다. optional 정책은 모두 미실행이면
`SKIP`/`ESTIMATED`, clean 실행과 미실행 혼합이면 `WARN`/`ESTIMATED`, 실제 failure와
미실행 혼합이면 `FAIL`/`ESTIMATED`로 남긴다.

pytest도 verbose/terminal summary에서 `SKIPPED`를 미실행, `XFAIL`을 실행된 예상 실패이자
PASS, `XPASS`를 실행된 FAIL로 정규화한다. 세 상태의 per-test marker와 summary token 모두
ordinary `passed` case가 없어도 parseable execution evidence로 인정한다. terminal summary가
있으면 마지막 권위 summary의 상태별 count만 사용하고, collection/interruption/detail line의
반복 숫자는 test 또는 failure로 중복 합산하지 않는다. 수집된 Python/C++ test가 전부 skip이면
`test` engine은 required에서 `ERROR`/`NOT_RUN`, optional에서 `SKIP`/`ESTIMATED`로 집계하지만,
실제 test/collection failure가 있으면 그 failure가 all-skipped shortcut보다 우선한다.
coverage 생성물이나 기존 coverage JSON은 이 상태를 대체하는 실행 증거가 아니다.

pytest module이 없어지는 경우의 unittest fallback도 같은 실행 상태를 보존한다. verbose
`... ok`는 실행된 PASS, `... skipped`는 미실행 SKIP, `... expected failure`는 실행된 예상

### I2-2 현재 인수인계 상태 — shared analysis context와 artifact manifest 완료

`refactor/analysis-context`에서 한 실행의 project/capability/compile 입력을 immutable
`AnalysisContext`로 고정했다. `ProjectModel`은 canonical root와 project-relative source,
header, include scope를 한 번 발견하고, 기존 bounded probe의 `CapabilityInventory`는
동일 객체로 공유한다. `CompilationContext`는 compile unit을 immutable tuple로 보존한다.

adapter의 실행 중 변경 상태는 mutable `BuildSession`에만 남는다. build/test/sanitize는
`RELEASE`/`COVERAGE`/`SANITIZE`를 명시적으로 선택하고 서로 다른 shadow/flags를 사용한다.
성공한 project/shadow regular file은 frozen `ArtifactManifest`로 발행되며 variant, producer,
source/config/toolchain identity, SHA-256, size, mode를 함께 기록한다. project/shadow 밖의
경로와 symlink escape는 거부된다.

JSON reporter는 optional `ici.analysis-context/v1` context와 `ici.artifacts/v1` manifest를
`ici.result/v3`에 추가한다. project/source/compile/artifact 경로는 project-relative POSIX
형식이고, 외부 include/search path는 context JSON projection에서 `-I[external]`로 치환된다.
기존 HTML editor-link absolute path와 tool evidence redaction 계약은 바꾸지 않는다. 기존 v3
report는 두 optional 확장이 없어도 읽을 수 있다. 리포터는 immutable context를 직접 변경하지
않고 projection만 생성한다.

I2-2의 최종 병합 조건은 full suite green인 CI/PR 검증이다. 정확한 테스트 수는 작업 중인
브랜치의 최종 CI artifact를 기준으로 기록하며 이 handover에는 고정하지 않는다.

### I2-3 현재 인수인계 상태 — 선언형 verification pipeline

작업 브랜치는 `refactor/verification-pipeline`다. `src/ici/core/pipeline.py`의 frozen
`EngineDescriptor`가 엔진별 `name`, `dependencies`, `produces`/`consumes`,
`profiles`, `execution`, `build_variant`를 선언한다. 내장 registry는 startup에서 중복
engine/artifact producer, unknown dependency, profile closure, 소비 artifact와 producer
dependency의 불일치, cycle을 검증한다.

profile은 `fast`/`standard`/`deep` 중 엔진 set만 선택한다. 동일 rule의 threshold와
의미는 profile에 따라 변하지 않는다. `fast`는 현재 내장 `test`/`sanitize`/`cognitive`를

### I3-4 현재 인수인계 상태 — compiler-backed C++ lint/include graph 구현 완료

현재 작업대 `refactor/cpp-analysis-context`에는 I3-4 구현과 focused local test가 반영되어
있다. compilation database/context가 있으면 C++ lint가 모든 covered production translation
unit configuration의 normalized direct GCC/Clang argv를 capability probe와 대조해 sanitized
replay한다. `-c`·출력·dependency 생성은 제거하고, positive allowlist 밖의 option과
plugin/wrapper/toolchain 주입 등 unsafe flag는 fail-closed로 거부한다. compiler는 inherited
override를 배제한 minimal replacement environment와 closed stdin으로 실행하며, 위치 있는
diagnostics와 PASS를 보존한다. error-level context/unit diagnostic, context coverage 누락,
replay 거부, malformed/truncated 출력, timeout, spawn 또는 검증할 수 없는 nonzero 결과는
`ERROR`/`NOT_RUN`으로 fail-closed한다. warning-level context/unit diagnostic은 위치 있는

context가 있는데도 fixed c++17 또는 suffix fallback으로 조용히 바뀌지 않는다.

### I4-1 현재 인수인계 상태 — compiler/clang-tidy adapter 원격 완료 (historical base)

구현 브랜치 `feat/cpp-static-analysis`의 최종 head는 `b7ed26c68aa61f2d3f3f8e58afb4556a16c681cd`,
병합된 exact `main`은 `973cf2423728f9d808873f548bc00c7878cceadd`다. I4-1의 여섯 구현
항목과 local/PR/main evidence가 완료됐다. 아래 v0.9.0 release boundary와 B4 pending 표현은
당시 시점의 historical snapshot이며, 그 snapshot의 v0.9.1·B4 완료 상태는 뒤의 별도 절을 따른다.

I4-1은 immutable `AnalysisContext`의 exact `CompilationUnit`을 compiler와 clang-tidy가
공유하는 adapter 경계다. `LintEngine`은 compile database를 직접 다시 읽지 않고,
`CapabilityInventory`가 승인한 external compiler/clang-tidy와 sanitized replay argv만
실행한다. GCC 9+ compiler는 JSON diagnostics를 사용하고 Clang 또는 unknown-version
fallback은 bounded `parseable-fixits` text를 사용한다. `_cpp_diagnostics`는 JSON/text를
atomic하게 파싱하고 project-relative/external location, stable rule ID, child/note,
clang-analyzer family 및 fix-it을 보존한다.

clang-tidy는 `auto`/`required`/`off` 정책으로 exact compilation context의 covered production
unit만 검사한다. explicit checks가 built-in defaults보다 우선하고, explicit
`clang_tidy_config`가 project-root-bounded `.clang-tidy` discovery보다 우선한다. discovery는
project root 위로 올라가지 않으며, config containment·regular-file·size/NUL 경계와
`ExtraArgs`/`ExtraArgsBefore`·`InheritParentConfig` 거부를 적용한다. compiler diagnostics와
clang-tidy/analyzer diagnostics는 별도 `ToolEvidence`, family, category로 남는다. fix-it은 report/remediation
제안으로만 보존되고 source/context는 수정되지 않는다.

approved executable, positive replay allowlist, project/source/working-directory containment,
minimal environment, closed stdin, no-shell execution, argv/output/unit/global budget이
security/evidence 경계다. missing/malformed context 또는 output, compile mismatch,
timeout/truncation, spawn/검증 불가능한 종료와 budget 초과는 heuristic fallback 없이
`ERROR`/`NOT_RUN`으로 fail-closed한다. optional `auto`의 tool 부재는 warning, `required`의
tool 부재는 error로 기록한다. lint cache identity는 `.clang-tidy` project input과
`ici.engines._clang_tidy`/`ici.engines._clazy`/`ici.engines._cpp_diagnostic_categories`/

`3602c2cb1b6998a54f00bf809a88d81617bec58c891bfaf12bf22bc882e71890`)와 packaged smoke가
통과했다. 최종 no-cache self-check는 exit 0/WARN, 7 PASS·5 WARN·0 FAIL·0 ERROR·1 SKIP,
test `1768/1770`, TEM `4.84`, complexity max 25, exact UTF-8 title/Zero-CDN이다. 이전
`1750 passed, 7 skipped, 10 failed` 시도는 boundary-consumer mismatch를 발견한 historical
evidence다. [PR CI run `33616285870`](https://github.com/jihoon22-lee/ici/actions/runs/33616285870)와
exact-main [run `33617482194`](https://github.com/jihoon22-lee/ici/actions/runs/33617482194)은

[`clang-tidy related-note workthrough`](../../workthrough/2026-09-02-clang-tidy-related-notes.md)의

## 3. 결정과 그 이유 — 다시 논의하지 말 것

저장소만 읽으면 "왜 이렇게 했지?" 가 되는 것들이다. 전부 사용자가 정했거나 실측이 정했다.

**"로직은 core, Qt 는 얇은 껍데기" 원칙은 폐기됐다.** 사용자 판단이다 — Qt 는 GUI 툴킷이기
전에 프레임워크이고, 내부 개발에서는 Qt 5.15 로 core 까지 구현한다. 규칙을 지키는 것 자체가
목적이 되면 안 된다. **문서에서 그 문장을 지우는 것이 toy-projects 계획 Task 6 Step 3 이다.**

**단, `icirv` 의 core 는 Qt 를 쓰지 않는다.** 이건 규칙이 아니라 **한 바이너리의 요구**다.
`icirv` CLI 는 Qt 6 패키지가 없고 glibc 가 2.28 인 RHEL 8 에 정적 링크로 나가며, 릴리스
워크플로가 정적 링크가 아니면 빌드를 실패시킨다. 나중에 필요해지면 Qt 를 넣어도 되지만 그때
이 바이너리를 어떻게 할지 같이 정해야 한다.

**Qt 버전을 고정하지 않는다.** 여기는 Qt 6.10.2, 내부망은 Qt 5.15. `find_package(QT NAMES Qt6 Qt5 ...)`
로 설치된 것을 찾는다. `ici.toml` 의 `cpp_pkg_config` 는 둘을 나열하면 된다 —
`get_cpp_pkg_config_flags` 가 해석 실패한 패키지를 건너뛴다.

**헤더는 예외 없이 `include/<project>/` 아래.** `include/gui/` 가 아니라 접두사를 유지한
`include/<project>/gui/` 인 이유는, 그러지 않으면 트리에서 유일하게 접두사 없는 경로가 되어
규칙이 다시 둘이 되기 때문이다.

**진입점(`main()` 정의 번역 단위)은 커버리지 스코프에서 제외된다.** g++ 경로가 원래 그랬고,
어댑터가 세기 시작하면 **코드가 하나도 안 바뀌었는데 CMake 로 옮겼다는 이유만으로 커버리지가
떨어진다.** viewer 에서 실제로 branch 71.2%/func 84.5% 까지 내려갔었다.

**두 어댑터 모두 테스트 바이너리 단위로 센다.** qmake 는 처음에 QtTest 의 함수 단위로 셌는데,
그러면 CTest 와 비교가 안 된다. `make check` 전사를 기준으로 바꿔 통일했다.

**loglens 의 커버리지 임계값이 80/90 → 55/80 으로 내려가 있다.** 코드가 나빠져서가 아니라
어댑터가 GUI 를 빌드하면서 **테스트 없는 Qt 셸 165 statements 가 분모에 들어왔기** 때문이다.
`loglens/ici.toml` 에 파일별 수치와 근거를 적어 두었다. **다음 계획의 목표가 이걸 되돌리는
것이고, 실측이 못 미치면 되돌리지 못한다 — 그때는 도달값을 적는다.**

## 4. 물린 것들 — 다음에도 물릴 자리

**푸시 전에 자기 검증을 돌려라.** `uv run pytest` 와 `ruff` 만 통과시키고 푸시했다가 CI 가
실패했다. ici 자신의 `exception` 엔진이 내가 쓴 `except ValueError: pass` 를 잡았다. 게이트
전체는 이렇다.

```bash
uv run --python 3.10 pytest
uvx ruff check . && uvx ruff format --check .
./scripts/build-pyz.sh && ./scripts/smoke.sh
./dist/ici.pyz verify          # 기준선: Pass 7 · Warn 5 · Fail 0
```

**`ruff format .` 이 마크다운 안의 Python 코드 블록도 포맷한다.** 설계 문서가 클래스 메서드를
문맥째 인용하는데 들여쓰기가 벗겨져 메서드가 모듈 함수로 바뀌었다. `pyproject.toml` 의
`[tool.ruff.format] exclude = ["*.md"]` 로 막아뒀다 — **지우지 말 것.**

**`ici verify` 가 도는 중에 그 프로젝트 파일을 편집하지 마라.** 한 번 그래서 링커 에러를
레이스로 오진했고, 진짜 원인(`gui_main.cpp` 의 두 번째 `main()`)을 찾는 데 시간을 썼다.

**`gh pr merge` 가 하네스 권한 분류기에 한 번 차단됐다.** 되돌리기 어려운 작업이라 차단 자체는
합리적이다. 막히면 우회하지 말고 사용자에게 알리면 된다. 사용자가 명시적으로 맡긴 뒤에는
통과했다.

**`sudo` 가 암호를 요구한다.** 패키지 설치는 사용자에게 명령을 알려주고 실행을 부탁해야 한다.

## 5. 픽스처가 놓친 결함 — 이 저장소가 배운 것

어댑터 작업에서 결함 9건이 나왔고 전부 만들다 나왔다. 그중 둘은 **ici 의 픽스처가 통과한
채로 실물 프로젝트에서만 드러났다.**

- **qmake 는 Qt 링크 테스트를 `target_wrapper.sh` 로 실행한다.** ici 가 그 줄을 못 읽어
  `diskmap` 의 테스트 6개 중 5개만 셌다. 픽스처는 Qt 테스트가 하나뿐이라 XML 폴백이 구해줬다.
- **qmake 는 상대 경로로 컴파일한다.** `.gcov` 파일명이 `^#^#^#src#format.cpp` 가 되고 line
  커버리지가 통째로 유실됐다. **픽스처는 그 코드 경로를 실제로 지나갔는데도** 커버리지 존재
  여부만 단언하고 값을 안 봐서 통과했다.

두 번째가 교훈이다. **픽스처를 만들 때 "지나가는가" 가 아니라 "무엇을 단언하는가" 를 봐야 한다.**

## 6. 환경

WSL2 + WSLg 라 **GUI 앱이 Windows 데스크톱에 실제 창으로 뜬다** (`DISPLAY=:0`,
`WAYLAND_DISPLAY=wayland-0`). 헤드리스로 돌릴 때만 `QT_QPA_PLATFORM=offscreen` 을 준다.

| 도구 | 버전 | 비고 |
|---|---|---|
| cmake / ctest | 4.2.3 | |
| qmake6 | 6.10.2 | Qt 6 |
| Qt6 Widgets/Test | 6.10.2 | |
| qmake / Qt5 Widgets/Test | 5.15.18 | 설치됨, `/usr/bin/qmake`; ici #81에서 4/4 CTest 실측 |

Qt 5 CMake 검증은 Qt 6을 먼저 찾지 않게 `-DCMAKE_DISABLE_FIND_PACKAGE_Qt6=ON`을 사용하고,
configure log와 실제 link target에서 선택된 major를 확인한다. `CMAKE_PREFIX_PATH`만 주는 것은
Qt 6 선택을 확실히 막지 못한다.

이전 세션의 “Qt 5 미설치/미검증” 표현은 폐기한다. 현재 `/usr/bin/qmake`는 Qt 5.15.18을
보고하며, ici viewer는 [#81](https://github.com/jihoon22-lee/ici/pull/81)에서 Qt 5.15
강제 4/4와 Qt 6 4/4를 모두 통과했다. toy-projects의 동일 환경 및 실측 명령은
[#15](https://github.com/jihoon22-lee/toy-projects/pull/15)에 기록돼 있다. diskmap의 Qt 5
이벤트 좌표 호환성은 [#16](https://github.com/jihoon22-lee/toy-projects/pull/16), loglens 셸
상태 머신은 [#17](https://github.com/jihoon22-lee/toy-projects/pull/17), 두 프로젝트의 공통
Qt5/Qt6 강제 matrix는 [#18](https://github.com/jihoon22-lee/toy-projects/pull/18)에서
각각 검증돼 T0가 완료됐다.

## 9. 규약

`AGENTS.md`(ici)에 있는 것이 전부 유효하다. 특히 **`main` 직접 작업 금지**, Conventional
Commits, 기능 변경 시 `CHANGELOG.md` 동기화. toy-projects 도 같은 방식으로 PR 을 쓴다.

세부 checklist나 roadmap key마다 PR을 만들지 않는다. PR #151은 linker dead-function과
Python AST-shape duplicate를 함께 전달했고, PR #152는 Python/test-quality 보강을 전달했다.
이후 ici는 Python/test-quality, build/integration/reporting, 최종 acceptance/support의 3개 큰 delivery로 묶는다. 버전/릴리스
결정은 모든 gate 완료 후 이 delivery들과 별개로 검토한다.
toy-projects도 기존 앱 완성, AbiLens/Quality Zoo 확장, path-aware 최종 CI의 3개 큰 delivery로
묶는다. 커밋은 의미 있는 구현 단위를 유지하지만 PR 제목은 사용자·기술 결과를 설명하고
roadmap code를 primary/sole 내용으로 쓰지 않는다.
