### Current unmerged follow-up — sanitizer/test execution state (I4-4)

현재 `fix/sanitizer-test-execution-state` branch는 origin/main `41690c9` 위의
`c524c2c` 및 `ea78e88` 실행 상태 보정이다. `TestCaseResult`의 마지막 네 번째 필드
`executed: bool = true`는 기존 세 인자 positional 생성과 호환되며, `passed = false`인 실행
실패와 수집됐지만 실행되지 않은 case를 분리한다. `passed = true`·`executed = false` 조합은
불변식 위반으로 거부한다.

CTest JUnit `<skipped>`와 `status="notrun"`/skip/skipped/disabled/blacklisted, stdout의
`Not Run`/`Disabled`/`Skipped`는 `executed = false`다. QtTest의 skip/`<skipped>`도 미실행,
xfail은 실행된 예상 실패이자 통과, xpass는 실행된 실패이며 unknown result는
`executed = true`, `passed = false`인 실패로 fail-closed한다. `test` 엔진은
`extra.skipped_tests`와 suite별 `skipped`를 기록하고 HTML은 SKIP을 별도 amber 행으로
렌더링한다.

QtTest parser는 `-xunitxml`의 각 `<testcase>` 상태를 해석한다. qmake adapter에서는
`make check` transcript가 테스트 바이너리 하나를 권위 있는 scope로 세고, QtTest XML은
그 바이너리의 failure detail을 보강하는 데만 사용한다. 따라서 QtTest와 자체 `main()`이
섞인 qmake 프로젝트에서 모든 function-level skip을 개별 scope로 집계한다고 주장하지 않는다.

sanitizer는 build 성공을 test 실행 증거로 간주하지 않는다. required 정책은 모든 case가
미실행이거나 실행된 case와 미실행 case가 섞인 경우 모두 `ERROR`/`NOT_RUN`으로 올리며,
실행된 실제 failure target은 `FAIL`로 보존한다. optional 정책은 모두 미실행이면
`SKIP`/`ESTIMATED`, clean 실행과 미실행 혼합이면 `WARN`/`ESTIMATED`, 실제 failure와
미실행 혼합이면 `FAIL`/`ESTIMATED`로 남긴다.

pytest도 verbose/terminal summary에서 `SKIPPED`를 미실행, `XFAIL`을 실행된 예상 실패이자
PASS, `XPASS`를 실행된 FAIL로 정규화한다. 수집된 Python/C++ test가 전부 skip이면 `test`
engine은 required에서 `ERROR`/`NOT_RUN`, optional에서 `SKIP`/`ESTIMATED`로 집계하며,
coverage 생성물이나 기존 coverage JSON은 이 상태를 대체하는 실행 증거가 아니다.

로컬 실행 증거는 Python `3.10.21`, 새 focused/real-CMake execution-state 파일 `18 passed`,
관련 `test_build_adapter`, `test_build_adapter_e2e`, `test_sanitize_engine`, `test_test_engine`,
`test_reporters`, `test_execution_state` 묶음 전체 통과, Qt `6.10.2` 실제 QtTest fixture의
`-xunitxml`에서 QSKIP은 `<skipped message>`를, XFAIL은 failure 없는 pass를, XPASS는
`<failure type="xpass">`를 낸 것을 확인했고, Ruff check/format도 통과했다. 이 follow-up의 PR CI,
sticky comment, Pages, extracted artifact byte-match는 아직 확인하지 않았고, 이 문서에서
full release gate를 주장하지 않는다. 버전은 `0.10.2`이며 release는 만들지 않는다.

### I2-4 현재 인수인계 상태 — user-local analysis cache 및 PR evidence 완료

작업 브랜치 `feat/analysis-cache`에 엔진 결과용 `AnalysisCache`가 추가됐다. `ici verify`는
기본적으로 user-local `~/.cache/ici/analysis/entries-v1/`를 사용하고, `XDG_CACHE_HOME` 또는
`ICI_CACHE_DIR`로 로컬 위치를 재지정할 수 있다. remote/shared cache는 없다. `ici verify
--no-cache`는 해당 실행의 cache lookup과 write를 모두 끄며, `ici cache`는 inventory와
invalidation 기준을 보여 주고 `ici cache --clear`는 exact entries directory의 JSON/TMP
entry만 정리한다.

key(`ici.analysis-cache-key/v2`)에는 canonical project root, project source와 인식된
source/build-config content digest, profile을 포함한 effective ici config, capability
inventory의 toolchain version/details, engine descriptor·implementation source, build
variant, compilation database path/content/parse state와 ici producer version이 들어간다.
따라서 source/config/policy/toolchain/implementation/variant/compile context/version이 달라지면
cache miss가 된다.

`cache_identity.py`는 입력·key, `cache_codec.py`는 32 MiB bounded strict JSON trust
boundary, `cache.py`는 store/inventory/clear와 atomic 수명을 맡는다. duplicate JSON key,
`NaN`/`Infinity`, symlink·비정규·oversize entry를 거부하며 새 entries directory와 파일은
0700/0600으로 만든다. `verify_report.json`과 engine별 생성 report는 source 입력에서 제외해
report 작성이 다음 cache key를 스스로 무효화하지 않는다. native finding만 저장하므로 legacy
target projection이 hit 때 중복되지 않는다.

완료된 `PASS`/`WARN`/`FAIL`은 evidence가 완전하고 artifact manifest가 유효할 때만 저장·재사용할
수 있다. `ERROR`/`SKIP`/`NOT_RUN`, timeout·truncated output·tool error, invalid/stale artifact는
성공 cache로 저장하지 않는다. 손상·stale·symlink entry는 miss로 처리한다.

entry는 user-local 임시 파일에 쓰고 flush·`fsync` 후 atomic replace하며, source/config는
read-only digest한다. hash 도중 입력 변경을 감지하면 그 실행의 cache를 끄고, artifact manifest는
hit/store 경계에서 실제 파일 identity를 다시 검증한다. 이 경계는 project source를 변경하지
않는다.

### I3-4 현재 인수인계 상태 — compiler-backed C++ lint/include graph 구현 완료

현재 작업대 `refactor/cpp-analysis-context`에는 I3-4 구현과 focused local test가 반영되어
있다. compilation database/context가 있으면 C++ lint가 모든 covered production translation

context가 있는데도 fixed c++17 또는 suffix fallback으로 조용히 바뀌지 않는다.

cycle의 exact 경로는 configuration별 compiler `-E -H` trace를 사용해 active resolved include
edge를 기록하고 `project`/`generated`/`system`/`third_party` scope를 집계한다. 각
configuration graph를 독립적으로 분석하고 동일 cycle component만 중복 제거하며 configuration

공유하는 adapter 경계다. `LintEngine`은 compile database를 직접 다시 읽지 않고,
`CapabilityInventory`가 승인한 external compiler/clang-tidy와 sanitized replay argv만
실행한다. GCC 9+ compiler는 JSON diagnostics를 사용하고 Clang 또는 unknown-version
fallback은 bounded `parseable-fixits` text를 사용한다. `_cpp_diagnostics`는 JSON/text를
atomic하게 파싱하고 project-relative/external location, stable rule ID, child/note,
clang-analyzer family 및 fix-it을 보존한다.

clang-tidy는 `auto`/`required`/`off` 정책으로 exact compilation context의 covered production
unit만 검사한다. explicit checks가 built-in defaults보다 우선하고, explicit
`clang_tidy_config`가 project-root-bounded `.clang-tidy` discovery보다 우선한다. discovery는
project root 위로 올라가지 않으며, config containment·regular-file·size/NUL 경계와
`ExtraArgs`/`ExtraArgsBefore`·`InheritParentConfig` 거부를 적용한다. compiler diagnostics와
clang-tidy/analyzer diagnostics는 별도 `ToolEvidence`, family, category로 남는다. fix-it은 report/remediation
제안으로만 보존되고 source/context는 수정되지 않는다.

approved executable, positive replay allowlist, project/source/working-directory containment,
minimal environment, closed stdin, no-shell execution, argv/output/unit/global budget이
security/evidence 경계다. missing/malformed context 또는 output, compile mismatch,
timeout/truncation, spawn/검증 불가능한 종료와 budget 초과는 heuristic fallback 없이
`ERROR`/`NOT_RUN`으로 fail-closed한다. optional `auto`의 tool 부재는 warning, `required`의
tool 부재는 error로 기록한다. lint cache identity는 `.clang-tidy` project input과
`ici.engines._clang_tidy`/`ici.engines._cpp_diagnostics`를 포함한 declared helper source
digest를 반영한다.

후속 adversarial review에서 compiler replay의 unit/global budget 부재와 context-level error 뒤
부분 실행, GCC unlocated/ICE kind, clang-tidy parent config inheritance 공백을 발견해 닫았다.
compiler와 clang-tidy는 각각 2,048 units·unit당 120초·전체 600초로 제한되며, context error가

### I4-2 현재 인수인계 상태 — Qt clazy와 generated-code contract

구현 브랜치 `feat/qt-analysis`는 [PR #122](https://github.com/jihoon22-lee/ici/pull/122)로
검증된 뒤 `9b3a88f7b216a9a82a988fe2d6d1ba7b35cc2327`로 squash merge됐다. 구현은 I3의 immutable `AnalysisContext`와
`CompilationUnit`을 단일 입력으로 유지하며, `LintEngine`이 compiler·clang-tidy·clazy·Qt
generated-code verifier에 같은 context를 전달한다. 소스나 compilation database를 adapter가
다시 발견하거나 수정하지 않는다.

`clazy` capability는 canonical 이름 하나로 `clazy-standalone`을 먼저 probe하고, 배포판의
`clazy` compiler-wrapper를 resolved alias/provider로 구분한다. `clazy = auto|required|off`는
선택/필수/비활성 정책이다. `clazy_profile = level0|level1`은 global `ici.profile`과 독립하고
기본값은 level0이다. level2 또는 noisy/manual check는 bounded `clazy_checks`를 명시해야만
선택된다. standalone은 `--checks`·`--only-qt`·source·`--` 뒤의 sanitized compiler args를
사용하고, wrapper는 approved `clang++`를 `CLANGXX`로 고정하면서 `CLAZY_CHECKS`를
replacement environment로 전달한다.

두 provider 모두 approved executable, exact covered production context, positive replay
allowlist, project/source/working-directory containment, no-shell 실행, closed stdin, no `-p`,
no `--fix`를 지킨다. clazy parser는 `-Wclazy-*` rule과 located parent/note를 atomic하게
검증해 `family = clazy`, stable rule ID, project-relative source/line target과 `ToolEvidence`를
남긴다. rule token은 QObject/connect/signal/slot을 `CORRECTNESS`, lifetime/ownership을
`RESOURCE`, Qt6/deprecated/QString API를 `COMPATIBILITY`, 나머지(예: container detach/
temporary)를 `MAINTAINABILITY`로 매핑한다. 최대 2,048 units·unit당 120초·전체 600초와
1,000,000자 output bound를 넘거나 context/coverage/replay/process/parser가 실패하면
heuristic으로 숨기지 않고 `ERROR`/`NOT_RUN`으로 닫는다.

Qt generated-code verifier는 source scope의 `.ui`, `.qrc`, 실제 코드의 `Q_OBJECT` 선언을
bounded하게 찾고, exact compilation database의 bounded indirect translation-unit include와
generated unit linkage를 검증한다. `ui_<stem>.h`, `qrc_<stem>.cpp`, `moc_<stem>.cpp`·`<stem>.moc`·
`mocs_compilation.cpp`를 각각 원본 입력 파일과 선언 라인으로 보고한다. CMake
AUTOMOC/AUTOUIC/AUTORCC와 qmake direct generated unit을 모두 다루며, exact include/define와
successful compiler replay로 Qt 5/Qt 6 major를 구분한다. 성공 replay가 있을 때만 linkage와
`QtCompatibility:Qt5`/`QtCompatibility:Qt6` PASS를 만들고, major 불명확·replay 부재·중복
generated stem은 WARN으로 남긴다. `.ui`와 `.qrc`는 source digest/cache identity에 포함되고,
lint cache identity에는
`_clazy`, `_cpp_tooling`, `_qt_codegen` 및 진단 helper source가 포함된다.

현재 full local run은 `1513 passed, 4 skipped`였으며, skip은 로컬 환경의
`clang-tidy`·`clazy`·`clang++` 미설치다.
CI/release workflow에는 clazy 설치와 `ICI_REQUIRE_STATIC_ANALYSIS_TOOLS=1`이 이미 반영되어
실제 process E2E를 skip하지 않도록 되어 있다. PR #122의 head `c3a8fe21639cecef395f0bc28777066401927da0`은
run `33499500259`에서 1,517/1,517 테스트(네 개 actual compiler/clang-tidy/clazy process

### C++ maintainability: merged scope-policy (I4-3) and remaining aggregate

PR #130의 `feat/compiler-backed-cpp-functions`는 위 exact-main acceptance 뒤
`8083267d864d3f29e6f3ae7c53358ce0b1674b44`로 병합됐다. PR #131의
`feat(complexity): classify C++ function scopes and metric provenance`는
`41690c9c2848fbc0332db4b80a4a1e2ed35db5d7`로 병합됐다. 이 scope-policy slice는 C++
`complexity` 함수 경계를
exact `CompilationContext`와 capability-approved direct `clang-tidy`의
`readability-function-size` AST geometry로 우선 확인한다. AST는 경계만 제공하며 CC/nesting은
`metric_confidence = "medium"`인 masked token/brace metric이다. `auto`는 context/tool 부재에만
heuristic scanner로 폴백하고, `required`는 unavailable 또는 partial/estimated boundary를
오류로 올리며, `off`는 의도적으로 heuristic 경로를 사용한다. 시도된 tool/replay/parser/
timeout/truncation/budget 오류는 silent fallback 없이 fail-closed한다. 단, clang-tidy가 visible
project diagnostics와 함께 정확한 `Suppressed N warnings (N in non-user code).`를 보고하는 경우는
외부/system 진단만 억제한 정형 회계로 허용한다. NOLINT/project/mixed/malformed/count-mismatch
suppression은 계속 `ERROR`/`NOT_RUN`으로 fail-closed한다.

이 후속 slice의 scope policy는 source-spelled named function만 target으로 유지하면서 function
template, conversion/call/subscript operator, literal operator를 포함하고
`function_kind`/template/provenance를 보존한다. lambda는 독립 target이 아니며 body는 enclosing
function의 CC/nesting에서 제외하고 `extra.cpp_scope_exclusions.lambda` count를 공개한다.
Expansion-site macro-generated function은 명시적으로 제외하고
`extra.cpp_scope_exclusions.macro_generated_function`에 count를 남기며, 다음 brace로 body를 추정하지
않는다. Fallback scanner는 operator 이름을 보존하고 multiline preprocessor
definition/continuation과 standalone macro invocation을 skip한다.

probe는 caller의 bounded source snapshot과 mapped-source cache를 사용하고 replay 전·도구 완료 후
source identity를 재검증한다. C++ 전체 source inventory는 source 2,048개·aggregate UTF-8 bytes 64 MiB
cap 아래에서 수집하며, 성공한 configuration 사이의 geometry/name/kind/provenance가 모두 일치할
때만 exact로 승격한다. configuration별 clang-tidy lines/statements/parameters는
`configuration_metrics`에 보존한다. 누락 또는 config별 상이한 geometry는 partial이고, metric 값이
다르거나 conditional-preprocessor body면 metric confidence가 low가 된다. compiler-backed function
metrics 또는 configuration coverage가 partial/low-confidence로 남으면 `required`에서는 이
경로가 오류다. approved tool executable은
각 process 실행 직전에 다시 resolve해 device/inode/mode/size/mtime/ctime identity를 확인하며, 변경·부재는
오류다. 한도는 2,048 units, source당 8 MiB, run source bytes 64 MiB, mapped-source cache bytes
16 MiB, output 1,000,000자, parser 10초, unit당 120초, 전체 600초다. same-line/overload,
braced declarator·default/noexcept/trailing `requires`, function-try/catch, `<%`/`%>` digraph body와
assigned `[]`/`+[]` lambda initializer phantom 배제를
매핑하며, `dir_fd`/`O_DIRECTORY`가 없는 fallback에서도 resolved named path identity를 재검증해
intermediate symlink/TOCTOU를 fail-closed한다.

## 3. 결정과 그 이유 — 다시 논의하지 말 것

저장소만 읽으면 "왜 이렇게 했지?" 가 되는 것들이다. 전부 사용자가 정했거나 실측이 정했다.

**"로직은 core, Qt 는 얇은 껍데기" 원칙은 폐기됐다.** 사용자 판단이다 — Qt 는 GUI 툴킷이기
전에 프레임워크이고, 내부 개발에서는 Qt 5.15 로 core 까지 구현한다. 규칙을 지키는 것 자체가
목적이 되면 안 된다. **문서에서 그 문장을 지우는 것이 toy-projects 계획 Task 6 Step 3 이다.**

**단, `icirv` 의 core 는 Qt 를 쓰지 않는다.** 이건 규칙이 아니라 **한 바이너리의 요구**다.
`icirv` CLI 는 Qt 6 패키지가 없고 glibc 가 2.28 인 RHEL 8 에 정적 링크로 나가며, 릴리스
워크플로가 정적 링크가 아니면 빌드를 실패시킨다. 나중에 필요해지면 Qt 를 넣어도 되지만 그때
이 바이너리를 어떻게 할지 같이 정해야 한다.

**Qt 버전을 고정하지 않는다.** 여기는 Qt 6.10.2, 내부망은 Qt 5.15. `find_package(QT NAMES Qt6 Qt5 ...)`
로 설치된 것을 찾는다. `ici.toml` 의 `cpp_pkg_config` 는 둘을 나열하면 된다 —
`get_cpp_pkg_config_flags` 가 해석 실패한 패키지를 건너뛴다.

**헤더는 예외 없이 `include/<project>/` 아래.** `include/gui/` 가 아니라 접두사를 유지한
`include/<project>/gui/` 인 이유는, 그러지 않으면 트리에서 유일하게 접두사 없는 경로가 되어
규칙이 다시 둘이 되기 때문이다.

**진입점(`main()` 정의 번역 단위)은 커버리지 스코프에서 제외된다.** g++ 경로가 원래 그랬고,
어댑터가 세기 시작하면 **코드가 하나도 안 바뀌었는데 CMake 로 옮겼다는 이유만으로 커버리지가
떨어진다.** viewer 에서 실제로 branch 71.2%/func 84.5% 까지 내려갔었다.

**두 어댑터 모두 테스트 바이너리 단위로 센다.** qmake 는 처음에 QtTest 의 함수 단위로 셌는데,
그러면 CTest 와 비교가 안 된다. `make check` 전사를 기준으로 바꿔 통일했다.

**loglens 의 커버리지 임계값이 80/90 → 55/80 으로 내려가 있다.** 코드가 나빠져서가 아니라
어댑터가 GUI 를 빌드하면서 **테스트 없는 Qt 셸 165 statements 가 분모에 들어왔기** 때문이다.
`loglens/ici.toml` 에 파일별 수치와 근거를 적어 두었다. **다음 계획의 목표가 이걸 되돌리는
것이고, 실측이 못 미치면 되돌리지 못한다 — 그때는 도달값을 적는다.**

## 4. 물린 것들 — 다음에도 물릴 자리

**푸시 전에 자기 검증을 돌려라.** `uv run pytest` 와 `ruff` 만 통과시키고 푸시했다가 CI 가
실패했다. ici 자신의 `exception` 엔진이 내가 쓴 `except ValueError: pass` 를 잡았다. 게이트
전체는 이렇다.

```bash
uv run --python 3.10 pytest
uvx ruff check . && uvx ruff format --check .
./scripts/build-pyz.sh && ./scripts/smoke.sh
./dist/ici.pyz verify          # 기준선: Pass 7 · Warn 5 · Fail 0
```

**`ruff format .` 이 마크다운 안의 Python 코드 블록도 포맷한다.** 설계 문서가 클래스 메서드를
문맥째 인용하는데 들여쓰기가 벗겨져 메서드가 모듈 함수로 바뀌었다. `pyproject.toml` 의
`[tool.ruff.format] exclude = ["*.md"]` 로 막아뒀다 — **지우지 말 것.**

**`ici verify` 가 도는 중에 그 프로젝트 파일을 편집하지 마라.** 한 번 그래서 링커 에러를
레이스로 오진했고, 진짜 원인(`gui_main.cpp` 의 두 번째 `main()`)을 찾는 데 시간을 썼다.

**`gh pr merge` 가 하네스 권한 분류기에 한 번 차단됐다.** 되돌리기 어려운 작업이라 차단 자체는
합리적이다. 막히면 우회하지 말고 사용자에게 알리면 된다. 사용자가 명시적으로 맡긴 뒤에는
통과했다.

**`sudo` 가 암호를 요구한다.** 패키지 설치는 사용자에게 명령을 알려주고 실행을 부탁해야 한다.

## 5. 픽스처가 놓친 결함 — 이 저장소가 배운 것

어댑터 작업에서 결함 9건이 나왔고 전부 만들다 나왔다. 그중 둘은 **ici 의 픽스처가 통과한
채로 실물 프로젝트에서만 드러났다.**

- **qmake 는 Qt 링크 테스트를 `target_wrapper.sh` 로 실행한다.** ici 가 그 줄을 못 읽어
  `diskmap` 의 테스트 6개 중 5개만 셌다. 픽스처는 Qt 테스트가 하나뿐이라 XML 폴백이 구해줬다.
- **qmake 는 상대 경로로 컴파일한다.** `.gcov` 파일명이 `^#^#^#src#format.cpp` 가 되고 line
  커버리지가 통째로 유실됐다. **픽스처는 그 코드 경로를 실제로 지나갔는데도** 커버리지 존재
  여부만 단언하고 값을 안 봐서 통과했다.

두 번째가 교훈이다. **픽스처를 만들 때 "지나가는가" 가 아니라 "무엇을 단언하는가" 를 봐야 한다.**

## 6. 환경

WSL2 + WSLg 라 **GUI 앱이 Windows 데스크톱에 실제 창으로 뜬다** (`DISPLAY=:0`,
`WAYLAND_DISPLAY=wayland-0`). 헤드리스로 돌릴 때만 `QT_QPA_PLATFORM=offscreen` 을 준다.

| 도구 | 버전 | 비고 |
|---|---|---|
| cmake / ctest | 4.2.3 | |
| qmake6 | 6.10.2 | Qt 6 |
| Qt6 Widgets/Test | 6.10.2 | |
| qmake / Qt5 Widgets/Test | 5.15.18 | 설치됨, `/usr/bin/qmake`; ici #81에서 4/4 CTest 실측 |

Qt 6 선택을 확실히 막지 못한다.

이전 세션의 “Qt 5 미설치/미검증” 표현은 폐기한다. 현재 `/usr/bin/qmake`는 Qt 5.15.18을

강제 4/4와 Qt 6 4/4를 모두 통과했다. toy-projects의 동일 환경 및 실측 명령은
[#15](https://github.com/jihoon22-lee/toy-projects/pull/15)에 기록돼 있다. diskmap의 Qt 5

상태 머신은 [#17](https://github.com/jihoon22-lee/toy-projects/pull/17), 두 프로젝트의 공통
Qt5/Qt6 강제 matrix는 [#18](https://github.com/jihoon22-lee/toy-projects/pull/18)에서
