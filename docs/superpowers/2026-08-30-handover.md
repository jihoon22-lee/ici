### I2-2 현재 인수인계 상태 — shared analysis context와 artifact manifest 완료

`refactor/analysis-context`에서 한 실행의 project/capability/compile 입력을 immutable
`AnalysisContext`로 고정했다. `ProjectModel`은 canonical root와 project-relative source,
header, include scope를 한 번 발견하고, 기존 bounded probe의 `CapabilityInventory`는
동일 객체로 공유한다. `CompilationContext`는 compile unit을 immutable tuple로 보존한다.

adapter의 실행 중 변경 상태는 mutable `BuildSession`에만 남는다. build/test/sanitize는
`RELEASE`/`COVERAGE`/`SANITIZE`를 명시적으로 선택하고 서로 다른 shadow/flags를 사용한다.
성공한 project/shadow regular file은 frozen `ArtifactManifest`로 발행되며 variant, producer,
source/config/toolchain identity, SHA-256, size, mode를 함께 기록한다. project/shadow 밖의
경로와 symlink escape는 거부된다.

JSON reporter는 optional `ici.analysis-context/v1` context와 `ici.artifacts/v1` manifest를
`ici.result/v3`에 추가한다. project/source/compile/artifact 경로는 project-relative POSIX
형식이고, 외부 include/search path는 context JSON projection에서 `-I[external]`로 치환된다.
기존 HTML editor-link absolute path와 tool evidence redaction 계약은 바꾸지 않는다. 기존 v3
report는 두 optional 확장이 없어도 읽을 수 있다. 리포터는 immutable context를 직접 변경하지
않고 projection만 생성한다.

I2-2의 최종 병합 조건은 full suite green인 CI/PR 검증이다. 정확한 테스트 수는 작업 중인
브랜치의 최종 CI artifact를 기준으로 기록하며 이 handover에는 고정하지 않는다.

### I2-3 현재 인수인계 상태 — 선언형 verification pipeline

작업 브랜치는 `refactor/verification-pipeline`다. `src/ici/core/pipeline.py`의 frozen
`EngineDescriptor`가 엔진별 `name`, `dependencies`, `produces`/`consumes`,
`profiles`, `execution`, `build_variant`를 선언한다. 내장 registry는 startup에서 중복
engine/artifact producer, unknown dependency, profile closure, 소비 artifact와 producer
dependency의 불일치, cycle을 검증한다.

profile은 `fast`/`standard`/`deep` 중 엔진 set만 선택한다. 동일 rule의 threshold와
의미는 profile에 따라 변하지 않는다. `fast`는 현재 내장 `test`/`sanitize`/`cognitive`를
제외하고, `standard`는 `cognitive`만 제외하며, `deep`는 전체 registry를 선택한다.
`analysis_context.profile`은 optional JSON field라서 기존 context 및 기존 v3 report를
계속 읽을 수 있다.

executor는 topological layer마다 독립적인 read-only engine을 최대 4개까지 병렬 실행하고,
build node는 read-only 작업이나 다른 build node와 겹치지 않게 직렬 실행한다. 결과는 registry
순서로 반환된다. engine 초기화/run 예외는 해당 결과를 `ERROR`와 `NOT_RUN` evidence로
남기며 공유 context와 다른 engine 결과를 보존한다. I2-3은 PR #96, 병합 commit
`edd775ac192baea4f9ce7dad882ab8e090d9c065`로 완료됐다. 최종 CI run `33343118306`은
898 tests, C++ fixtures, pyz build/smoke, self/viewer dogfood, Qt5·Qt6, report publication과
Merge Gate가 모두 성공했다. sticky comment `5472080848`의 두 Pages도 HTTP 200·`text/html`·
external refs 0건이었다. I2-4 cache/reproducibility evidence는 아래 완료 절을 따른다.

### I2-4 현재 인수인계 상태 — user-local analysis cache 및 PR evidence 완료

작업 브랜치 `feat/analysis-cache`에 엔진 결과용 `AnalysisCache`가 추가됐다. `ici verify`는
기본적으로 user-local `~/.cache/ici/analysis/entries-v1/`를 사용하고, `XDG_CACHE_HOME` 또는
`ICI_CACHE_DIR`로 로컬 위치를 재지정할 수 있다. remote/shared cache는 없다. `ici verify
--no-cache`는 해당 실행의 cache lookup과 write를 모두 끄며, `ici cache`는 inventory와
invalidation 기준을 보여 주고 `ici cache --clear`는 exact entries directory의 JSON/TMP
entry만 정리한다.

key(`ici.analysis-cache-key/v2`)에는 canonical project root, project source와 인식된
source/build-config content digest, profile을 포함한 effective ici config, capability
inventory의 toolchain version/details, engine descriptor·implementation source, build
variant, compilation database path/content/parse state와 ici producer version이 들어간다.
따라서 source/config/policy/toolchain/implementation/variant/compile context/version이 달라지면
cache miss가 된다.

`cache_identity.py`는 입력·key, `cache_codec.py`는 32 MiB bounded strict JSON trust
boundary, `cache.py`는 store/inventory/clear와 atomic 수명을 맡는다. duplicate JSON key,
`NaN`/`Infinity`, symlink·비정규·oversize entry를 거부하며 새 entries directory와 파일은
0700/0600으로 만든다. `verify_report.json`과 engine별 생성 report는 source 입력에서 제외해
report 작성이 다음 cache key를 스스로 무효화하지 않는다. native finding만 저장하므로 legacy
target projection이 hit 때 중복되지 않는다.

완료된 `PASS`/`WARN`/`FAIL`은 evidence가 완전하고 artifact manifest가 유효할 때만 저장·재사용할
수 있다. `ERROR`/`SKIP`/`NOT_RUN`, timeout·truncated output·tool error, invalid/stale artifact는
성공 cache로 저장하지 않는다. 손상·stale·symlink entry는 miss로 처리한다.

entry는 user-local 임시 파일에 쓰고 flush·`fsync` 후 atomic replace하며, source/config는
read-only digest한다. hash 도중 입력 변경을 감지하면 그 실행의 cache를 끄고, artifact manifest는
hit/store 경계에서 실제 파일 identity를 다시 검증한다. 이 경계는 project source를 변경하지
않는다.

로컬 Python 3.10 전체 테스트 935개, Ruff check/format, smoke 전체가 통과했다. `standard`
최초 실행은 118.49초·hits 0, 재실행은 2.38초·hits 12였고 normalized result SHA-256

## 3. 결정과 그 이유 — 다시 논의하지 말 것

저장소만 읽으면 "왜 이렇게 했지?" 가 되는 것들이다. 전부 사용자가 정했거나 실측이 정했다.

**"로직은 core, Qt 는 얇은 껍데기" 원칙은 폐기됐다.** 사용자 판단이다 — Qt 는 GUI 툴킷이기
전에 프레임워크이고, 내부 개발에서는 Qt 5.15 로 core 까지 구현한다. 규칙을 지키는 것 자체가
목적이 되면 안 된다. **문서에서 그 문장을 지우는 것이 toy-projects 계획 Task 6 Step 3 이다.**

**단, `icirv` 의 core 는 Qt 를 쓰지 않는다.** 이건 규칙이 아니라 **한 바이너리의 요구**다.
`icirv` CLI 는 Qt 6 패키지가 없고 glibc 가 2.28 인 RHEL 8 에 정적 링크로 나가며, 릴리스
워크플로가 정적 링크가 아니면 빌드를 실패시킨다. 나중에 필요해지면 Qt 를 넣어도 되지만 그때
이 바이너리를 어떻게 할지 같이 정해야 한다.

**Qt 버전을 고정하지 않는다.** 여기는 Qt 6.10.2, 내부망은 Qt 5.15. `find_package(QT NAMES Qt6 Qt5 ...)`
로 설치된 것을 찾는다. `ici.toml` 의 `cpp_pkg_config` 는 둘을 나열하면 된다 —
`get_cpp_pkg_config_flags` 가 해석 실패한 패키지를 건너뛴다.

**헤더는 예외 없이 `include/<project>/` 아래.** `include/gui/` 가 아니라 접두사를 유지한
`include/<project>/gui/` 인 이유는, 그러지 않으면 트리에서 유일하게 접두사 없는 경로가 되어
규칙이 다시 둘이 되기 때문이다.

**진입점(`main()` 정의 번역 단위)은 커버리지 스코프에서 제외된다.** g++ 경로가 원래 그랬고,
어댑터가 세기 시작하면 **코드가 하나도 안 바뀌었는데 CMake 로 옮겼다는 이유만으로 커버리지가
떨어진다.** viewer 에서 실제로 branch 71.2%/func 84.5% 까지 내려갔었다.

**두 어댑터 모두 테스트 바이너리 단위로 센다.** qmake 는 처음에 QtTest 의 함수 단위로 셌는데,
그러면 CTest 와 비교가 안 된다. `make check` 전사를 기준으로 바꿔 통일했다.

**loglens 의 커버리지 임계값이 80/90 → 55/80 으로 내려가 있다.** 코드가 나빠져서가 아니라
어댑터가 GUI 를 빌드하면서 **테스트 없는 Qt 셸 165 statements 가 분모에 들어왔기** 때문이다.
`loglens/ici.toml` 에 파일별 수치와 근거를 적어 두었다. **다음 계획의 목표가 이걸 되돌리는
것이고, 실측이 못 미치면 되돌리지 못한다 — 그때는 도달값을 적는다.**

## 4. 물린 것들 — 다음에도 물릴 자리

**푸시 전에 자기 검증을 돌려라.** `uv run pytest` 와 `ruff` 만 통과시키고 푸시했다가 CI 가
실패했다. ici 자신의 `exception` 엔진이 내가 쓴 `except ValueError: pass` 를 잡았다. 게이트
전체는 이렇다.

```bash
uv run --python 3.10 pytest
uvx ruff check . && uvx ruff format --check .
./scripts/build-pyz.sh && ./scripts/smoke.sh
./dist/ici.pyz verify          # 기준선: Pass 7 · Warn 5 · Fail 0
```

**`ruff format .` 이 마크다운 안의 Python 코드 블록도 포맷한다.** 설계 문서가 클래스 메서드를
문맥째 인용하는데 들여쓰기가 벗겨져 메서드가 모듈 함수로 바뀌었다. `pyproject.toml` 의
`[tool.ruff.format] exclude = ["*.md"]` 로 막아뒀다 — **지우지 말 것.**

**`ici verify` 가 도는 중에 그 프로젝트 파일을 편집하지 마라.** 한 번 그래서 링커 에러를
레이스로 오진했고, 진짜 원인(`gui_main.cpp` 의 두 번째 `main()`)을 찾는 데 시간을 썼다.

**`gh pr merge` 가 하네스 권한 분류기에 한 번 차단됐다.** 되돌리기 어려운 작업이라 차단 자체는
합리적이다. 막히면 우회하지 말고 사용자에게 알리면 된다. 사용자가 명시적으로 맡긴 뒤에는
통과했다.

**`sudo` 가 암호를 요구한다.** 패키지 설치는 사용자에게 명령을 알려주고 실행을 부탁해야 한다.

## 5. 픽스처가 놓친 결함 — 이 저장소가 배운 것

어댑터 작업에서 결함 9건이 나왔고 전부 만들다 나왔다. 그중 둘은 **ici 의 픽스처가 통과한
채로 실물 프로젝트에서만 드러났다.**

- **qmake 는 Qt 링크 테스트를 `target_wrapper.sh` 로 실행한다.** ici 가 그 줄을 못 읽어
  `diskmap` 의 테스트 6개 중 5개만 셌다. 픽스처는 Qt 테스트가 하나뿐이라 XML 폴백이 구해줬다.
- **qmake 는 상대 경로로 컴파일한다.** `.gcov` 파일명이 `^#^#^#src#format.cpp` 가 되고 line
  커버리지가 통째로 유실됐다. **픽스처는 그 코드 경로를 실제로 지나갔는데도** 커버리지 존재
  여부만 단언하고 값을 안 봐서 통과했다.

두 번째가 교훈이다. **픽스처를 만들 때 "지나가는가" 가 아니라 "무엇을 단언하는가" 를 봐야 한다.**

## 6. 환경

WSL2 + WSLg 라 **GUI 앱이 Windows 데스크톱에 실제 창으로 뜬다** (`DISPLAY=:0`,
`WAYLAND_DISPLAY=wayland-0`). 헤드리스로 돌릴 때만 `QT_QPA_PLATFORM=offscreen` 을 준다.

| 도구 | 버전 | 비고 |
|---|---|---|
| cmake / ctest | 4.2.3 | |
| qmake6 | 6.10.2 | Qt 6 |
| Qt6 Widgets/Test | 6.10.2 | |
| qmake / Qt5 Widgets/Test | 5.15.18 | 설치됨, `/usr/bin/qmake`; ici #81에서 4/4 CTest 실측 |

Qt 5 CMake 검증은 Qt 6을 먼저 찾지 않게 `-DCMAKE_DISABLE_FIND_PACKAGE_Qt6=ON`을 사용하고,
configure log와 실제 link target에서 선택된 major를 확인한다. `CMAKE_PREFIX_PATH`만 주는 것은
Qt 6 선택을 확실히 막지 못한다.

이전 세션의 “Qt 5 미설치/미검증” 표현은 폐기한다. 현재 `/usr/bin/qmake`는 Qt 5.15.18을
보고하며, ici viewer는 [#81](https://github.com/jihoon22-lee/ici/pull/81)에서 Qt 5.15
강제 4/4와 Qt 6 4/4를 모두 통과했다. toy-projects의 동일 환경 및 실측 명령은
[#15](https://github.com/jihoon22-lee/toy-projects/pull/15)에 기록돼 있다. diskmap의 Qt 5
이벤트 좌표 호환성은 [#16](https://github.com/jihoon22-lee/toy-projects/pull/16), loglens 셸
상태 머신은 [#17](https://github.com/jihoon22-lee/toy-projects/pull/17), 두 프로젝트의 공통
Qt5/Qt6 강제 matrix는 [#18](https://github.com/jihoon22-lee/toy-projects/pull/18)에서
각각 검증돼 T0가 완료됐다.
