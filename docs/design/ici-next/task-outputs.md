# task 산출물: 있다는 것과 다 있다는 것

> #205 작업 4. 이 문서는 **task가 만든 것을 어디에 쓰고, 무엇을 근거로 "다 됐다"고 말하는가**를
> 정한다. 실행 자체는 [task-execution.md](task-execution.md)에 있다.

## 한 줄

> **reader가 믿는 이름으로는, 전부 다 있기 전까지 아무것도 존재하지 않는다.**

인수 기준은 셋을 나란히 적는다 — *"output path 이탈·symlink·부분 artifact를 거부한다."*
셋이 한 줄에 있는 이유는 **같은 실수의 세 가지 깊이**이기 때문이다.

|깊이|보기에는|실제로는|
|---|---|---|
|경로 이탈|`../out.json`|밖으로 나간다. **눈에 보인다.**|
|symlink|`reports/out.json`|`..`가 없고 root 안이다. 그래도 `/etc`에 쓴다.|
|부분 artifact|경로도 맞고 파일도 있다|**절반만 있다.**|

`..`만 검사하는 구현은 첫 줄에서 멈춘다. 그리고 정작 **하중을 받는 검사는 두 번째**다.

## 왜 symlink가 목록에 따로 있는가

**root 안에 머무는 이름이 root 밖으로 resolve될 수 있다.** 이전 run이, 또는 도구 자신이
출력 트리에 링크를 하나 두면 `reports/out.json`은 `..` 하나 없이 `/etc/out.json`이 된다.

그래서 경로는 **가는 길의 모든 링크를 따라간 뒤에도** root 안에 있을 때만 받아들인다.
링크는 resolve해서 판단하지 않고 **거절**한다 — 지금 가리키는 곳이 도구가 도착할 때
가리키는 곳이라는 보장이 없기 때문이다.

root 자신의 realpath와 비교한다. **링크 뒤에 있는 root는 root이지 이탈이 아니다**(macOS의
`/tmp`). 검사 두 개는 각자 자기 형태의 root와 비교한다 — 섞으면 build 디렉터리가 링크
뒤에 있는 기계에서 **모든 쓰기가 거절된다**. 이건 테스트가 잡았다.

## 부분 artifact는 경로 문제가 아니다

경로도 맞고, 파일도 거기 있고, **존재를 확인하는 reader는 "예"를 받는다.**
`exit code를 답으로 읽는 것`과 같은 실수가 한 겹 바깥에 있는 것이다 — **있음을 완결로 읽기.**

그래서 manifest는 이름 목록이 아니라 **크기와 digest**를 적는다.

> 이름은 쓰기가 **시작됐다**는 증거다. digest는 **끝났다**는 증거다.

크기만으로는 부족하다. 같은 길이로 덮어쓴 파일은 크기 검사를 그냥 통과한다.

## 원자성: 이름이 내용보다 먼저 생기지 않는다

도구는 **private staging 디렉터리 안에서** 돈다. 도는 동안 **실제 이름을 가진 파일은
아예 없다** — reader가 일찍 찾을 것이 존재하지 않는다.

끝난 artifact는 제자리로 rename되고, **"이 집합은 완결이다"라고 말하는 manifest가 마지막에**
rename된다. 어느 순간에 도착한 reader든 **이전 run의 출력이거나 이번 run의 출력**을 보고,
**섞인 것은 보지 않는다.**

- staging이 root **안**에 있는 이유: `os.replace`가 원자적이려면 **같은 파일시스템**이어야
  한다. `/tmp`는 그걸 보장하지 않는다. (부차적으로, 공유 임시 디렉터리는 누구나 쓸 수 있어서
  **쓰려던 이름을 남이 먼저 차지**할 수 있다.)
- manifest를 쓴 뒤 `fsync`하는 이유: 안 하면 **이름이 내용보다 먼저 착지**할 수 있고,
  전원이 나간 기계는 이름은 갖고 내용은 잃는다.
- staged 파일을 `mkstemp`로 만들지 **않는** 이유: `mkstemp`는 0600으로 만들고 `os.replace`가
  그 mode를 유지한다. 그래서 첫 판은 **task를 돌린 사용자만 읽을 수 있는 manifest**를
  내놓았다 — 다른 사람이 읽으라고 있는 공유 build root 안에서 비공개로. **테스트가 잡았다.**
  이제 0o666으로 열어 커널이 umask를 적용하게 한다. manifest는 **자기가 설명하는 artifact보다
  더 비공개일 수 없다.**

## 승격: 무엇이 cache가 되는가

*"실패/취소 결과는 정상 cache로 승격하지 않는다."*

규칙은 exit code가 아니라 `Interpretation`에 대해 쓰여 있다. **violation을 찾아 exit 1을 낸
linter는 자기가 받은 질문에 답한 것**이고, 그걸 cache하지 않는 것은 **진짜 결과를 버리는
것**이다(작업 6의 구분이 여기서 무엇을 cache할지 결정한다).

|실행|승격|
|---|---|
|`succeeded`|O|
|`found-findings`|**O** — 도구는 완벽히 동작했다|
|`failed`|X|
|`did-not-run` (timeout·signal·truncation·start-failed·**cancelled**)|X|

`did-not-run` 쪽은 **enum 전체를 훑는 테스트**로 덮는다. 나중에 추가되는 이유가
**이미 cache 가능한 상태로 도착할 수 없다.**

## lock: 잡은 프로세스보다 오래 살면 안 된다

작업 3의 인수 기준이 *"취소 후 ... lock ... 정리 여부를 확인한다"*고 묻는다. 이 질문이
**뻔한 구현을 배제한다.**

`O_EXCL` lock 파일은 배타적이고, **홀더가 죽는 순간까지는** 정확하다. 취소가 하는 일이
정확히 그것이고, 그러면 파일은 남아 있고 **이후 모든 run이 존재하지 않는 프로세스를
기다린다.**

> **잡은 프로세스보다 오래 사는 lock은 lock이 없는 것보다 나쁘다.**
> lock이 없으면 가끔 경주에서 지고, 썩은 lock은 **영원히 모두를 막는다.**

그래서 배타성은 **열린 descriptor에 대한 OS의 것**이다. 프로세스가 사라지면 — 정상 종료든,
terminate든, **SIGKILL이든** — 커널이 놓고, descriptor 밖에 상태가 없었으므로 **정리할 것이
없다.** 기준도 이걸로 답한다: 자식에서 lock을 잡고, **취소가 하듯 그 자식을 죽이고**, 다른
쪽이 잡는 것을 본다.

어느 메커니즘도 없는 플랫폼에서는 **그냥 진행하지 않고 raise한다.** lock을 잡은 척하는 것이
lock이 막으려는 실패 그 자체다.

## 예외가 아니라 값

`produce()`에서 나가는 것은 예외가 아니다. **승격 거부는 실행에 대한 사실**이고 호출자가
보고해야 할 내용이다. 예외로 만들면 **부른 쪽의 crash**가 된다.

lock을 못 잡은 경우 `outcome`은 `None`이다 — **아무것도 실행되지 않았다.** 이걸 실패한 도구로
보고하면 **시작된 적도 없는 도구를 디버깅하러** 사람을 보낸다.
