# Public v0.11.0 release evidence

## Overview

v0.11.0은 공개 stable 릴리스다. [GitHub Release
v0.11.0](https://github.com/jihoon22-lee/ici/releases/tag/v0.11.0)은 exact `main` commit
`41cdff6d9deaab4ce2b46d2c7a9966ddd8d12efe`를 대상으로 게시됐고, provenance·artifact 검증이
모두 완료됐다. 이 문서는 현재 문서가 참조할 release 근거를 한곳에 고정하고, v0.10.2 evidence는
historical snapshot으로 보존한다.

`release: cut v0.11.0` commit이 예고한 대로, evidence block의 SHA-256과 run ID는 측정 전에는
쓸 수 없는 값이라 release run 성공 후인 지금 채운다.

## Context

release 시퀀스는 한 번에 통과하지 않았다. 그 경과도 증거의 일부이므로 함께 기록한다.

| 시도 | run | 결과 |
|---|---|---|
| 1 | [34307127661](https://github.com/jihoon22-lee/ici/actions/runs/34307127661) | `Validate Release Provenance` 실패 |
| 2 | 같은 run, rerun | provenance 통과, `Dogfood the Release Candidate` 실패 |
| 3 | [34310970522](https://github.com/jihoon22-lee/ici/actions/runs/34310970522) | **성공** |

- **1차**: PR #188을 squash merge한 직후 tag를 밀었다. provenance는 tag가 가리키는 **정확한
  commit**에 성공한 `Merge Gate`를 요구하는데, 그 commit의 main CI는 그때 막 시작했고
  provenance는 6분(36 × 10초)만 기다린다. tag 자체는 올바른 commit을 가리키므로 main CI 성공
  후 rerun으로 해결했다.
- **2차**: dogfood에서 `Suite: FAIL — required engine 'test' failed`. 리포트의 capability
  줄이 원인을 적고 있었다 — `ruff=unavailable`. `release.yml`이 프로젝트 `.venv/bin`을 PATH에
  올리지 않아, dogfood 안에서 재실행되는 프로젝트 스위트의 ruff 의존 테스트가 실패했다.
  `ci.yml`은 이 스텝을 갖고 있었고 `release.yml`은 없었다. #189로 고쳤다.
- **3차**: 수정된 `main`에서 `workflow_dispatch`(`version_tag=v0.11.0`)로 실행했다. tag는
  움직이지 않았다 — provenance가 tag를 스스로 resolve해 그 commit에 detach하므로, workflow
  정의는 수정된 `main`의 것이고 artifact는 tag commit에서 나온다.

v0.10.2가 이 결함 없이 나간 것은 release job이 건전해서가 아니라, ruff를 요구하는 테스트가
그때 아직 없었기 때문이다. 자세한 근거는 #189에 있다.

### Independent artifact verification

API가 보고한 digest를 그대로 받아쓰지 않고, asset을 내려받아 직접 계산했다. 세 값이 모두
같아야 한다 — 계산한 digest, API digest, 공개된 sidecar 내용.

```text
$ sha256sum ici.pyz
334bcda1bf127ff18ca1931cb55a8ac6e62af2d687ac90ab13c6af2e5499bc1f  ici.pyz
$ cat ici.pyz.sha256
334bcda1bf127ff18ca1931cb55a8ac6e62af2d687ac90ab13c6af2e5499bc1f  ici.pyz
$ sha256sum -c ici.pyz.sha256
ici.pyz: OK
$ ./ici.pyz --version
ici 0.11.0
```

`icirv`와 `icirv-gui`의 digest는 v0.10.2와 byte-identical이다. 이건 우연이 아니라 확인되는
사실이다 — `git diff v0.10.2 41cdff6 -- viewer/`는 `viewer/ici.toml`과 새 파일
`viewer/ici-static-cli.toml`만 바꿨고, C++ 소스는 한 줄도 건드리지 않았다. 같은 입력에서 같은
바이트가 나온 것이므로, 두 바이너리에 대해서는 빌드가 재현 가능하다는 증거이기도 하다.

`icirv-gui.README.txt`는 크기는 같은데 digest가 다르다(v0.10.2: `ec3fb3b2…`). 두 릴리스의
파일을 실제로 내려받아 비교하니 차이는 네 줄뿐이었다:

```text
< 	libQt6Widgets.so.6 => /lib/x86_64-linux-gnu/libQt6Widgets.so.6 (0x00007f987f400000)
> 	libQt6Widgets.so.6 => /lib/x86_64-linux-gnu/libQt6Widgets.so.6 (0x00007ff8fcc00000)
```

버전 문자열이 아니라 **`ldd` 출력에 그대로 실린 ASLR 로드 주소**다. 이 README는 빌드 시점의
`ldd` 결과를 담으므로 같은 입력이라도 실행마다 다른 바이트가 나온다 — 즉 아홉 자산 중 이
하나는 구조적으로 재현 불가능하다. 실제 의존성 목록(soname과 경로)은 동일하므로 문서가 전하는
정보 자체는 바뀌지 않았지만, digest 비교로 이 자산의 무결성을 릴리스 간에 추적할 수는 없다.

## Next Steps

`icirv`/`icirv-gui`가 v0.10.2와 byte-identical이라는 것은 viewer 쪽에 이 릴리스가 담은 변화가
없다는 뜻이기도 하다. 다음 릴리스에서 viewer 범위를 다룰 때 이 digest를 비교 기준으로 쓸 수
있다.

toy-projects의 ici pin은 여전히 공개 `v0.10.2`를 가리킨다. v0.11.0으로 올릴지는 별도 결정이며,
올린다면 `ICI_VERSION`/`ICI_PYZ_SHA256`을 위 표의 값으로 바꾸는 변경이 된다.
